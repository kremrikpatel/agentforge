## Objective
Build Phase 3 of "AgentForge": an admin-configurable Actions/Connectors layer so agents can call real third-party APIs and custom actions reliably, with retries, timeouts, schema validation, and graceful degradation.

## Context (carry forward)
- Phase 1: LangGraph 4-agent pipeline, LLM gateway with fallback, guardrails, three-tier memory, Docker Compose stack, all under `agentforge/`.
- Phase 2: RAG retrieval module at `agentforge/rag/` exposed as a tool to agent nodes.
- Remaining phases (red-teaming, admin UI, instrumentation, K8s deploy) are out of scope here.
- Backend is Python, agent orchestration is LangGraph — actions will be bound as LangGraph tools, same pattern as the Phase 2 retrieval tool.

## Target State
An actions layer that:
- Defines an `Action` schema (Pydantic): name, description, input schema, output schema, auth requirements, timeout, retry policy.
- Ships reference connectors for Shopify and Stripe (read-only operations, e.g. list orders / list charges) built against this schema.
- Supports custom actions defined via config (JSON/YAML) without code changes — an admin can register a new REST action (URL template, method, headers, auth type) and it becomes callable by agents.
- Implements retry with exponential backoff and jitter, per-action configurable timeout, and circuit-breaker style graceful degradation (an action failing repeatedly is temporarily disabled and the agent is told to proceed without it rather than hang).
- Validates all inputs and outputs against the declared schema before/after the call; rejects and logs schema violations.
- Exposes a `dispatch_action(action_name, args)` interface as a LangGraph tool, mirroring how the Phase 2 retrieval tool is bound.
- Supports agent-to-agent calls as a special action type (calling another AgentForge pipeline run).

## Scope
- Work only in: `agentforge/actions/` (new), `agentforge/agents/` (only to bind the dispatch tool)
- Do NOT touch: `agentforge/rag/`, `agentforge/gateway/`, `agentforge/memory/`

## Constraints
- Python 3.11+, reuse existing guardrails module for validating action inputs/outputs where relevant (e.g. PII in outbound payloads)
- All credentials for Shopify/Stripe/custom actions referenced via env vars only — never hardcoded; document required vars in `.env.example`
- No live calls to real Shopify/Stripe accounts in tests — mock the HTTP layer
- No new dependencies beyond an HTTP client and a JSON schema validator, without asking first
- Only make changes directly requested. Do not add features or refactor beyond what's asked.

## Acceptance Criteria
- [ ] Custom action can be registered via config file alone and successfully dispatched, with no code changes
- [ ] A simulated timeout triggers the configured retry/backoff, verified by test
- [ ] A repeatedly failing action trips the circuit breaker and the pipeline continues without hard-failing (test included)
- [ ] Malformed input/output against an action's schema is rejected with a clear error, not silently passed through
- [ ] Shopify and Stripe reference connectors work against mocked responses
- [ ] Agent-to-agent action type successfully triggers a nested pipeline run in a test
- [ ] `pytest` passes for retries, circuit breaker, schema validation, and dispatch
- [ ] README section documents how to register a new custom action

## Stop Conditions
Stop and ask before:
- Deleting any file
- Adding any dependency not listed in Constraints
- Making any real (non-mocked) outbound call to Shopify/Stripe
- Touching anything outside `agentforge/actions/` and the agreed tool-binding point
