## Objective
Build Phase 4 of "AgentForge": a PyRIT-based red-team dashboard that continuously stress-tests the pipeline (jailbreak, XPIA, crescendo, skeleton-key attacks) and reports whether guardrails hold.

## Context (carry forward)
- Phase 1: LangGraph 4-agent pipeline behind FastAPI, LLM gateway with fallback, guardrails layer at `agentforge/guardrails/`, three-tier memory.
- Phase 2: RAG tool at `agentforge/rag/`. Phase 3: Actions/connectors tool at `agentforge/actions/`.
- Admin UI, instrumentation, and K8s deploy are later phases, out of scope here.
- The target under test is the FastAPI endpoint `POST /pipeline/run` from Phase 1.

## Target State
A red-team subsystem that:
- Uses PyRIT to run four attack categories against `/pipeline/run`: jailbreak prompts, XPIA (cross-prompt injection via retrieved/tool content), crescendo (multi-turn escalation), and skeleton-key style guardrail-bypass attempts.
- Runs as a scheduled/on-demand job (not inline with production traffic) against a test/staging instance of the pipeline.
- Scores each attack attempt as blocked/leaked using the existing guardrails layer's pass/fail signal plus a secondary LLM-judge check for leaked content the guardrails missed.
- Produces a dashboard (can be a lightweight FastAPI+HTML page or a Streamlit app — pick one and justify briefly) showing attack category, pass rate, and example transcripts for failures.
- Logs every attack attempt and result to Postgres for trend tracking across runs.
- Fails a CI-style check (non-zero exit code) if the block rate for any category drops below a configurable threshold — for future CI wiring, not required to wire into CI now.

## Scope
- Work only in: `agentforge/redteam/` (new)
- Do NOT touch: `agentforge/agents/`, `agentforge/rag/`, `agentforge/actions/`, `agentforge/guardrails/` internals (call into guardrails, don't modify it)

## Constraints
- Python 3.11+, PyRIT for attack orchestration, reuse the existing LLM gateway for the secondary judge check — no second gateway
- Attacks must run against a designated test/staging config, never a flag that could accidentally point at a production credential set
- No new dependencies beyond PyRIT and the dashboard framework chosen, without asking first
- Only make changes directly requested. Do not add features or refactor beyond what's asked.

## Acceptance Criteria
- [ ] All four attack categories run end-to-end against the Phase 1 pipeline and produce a pass/fail per attempt
- [ ] Dashboard displays aggregate pass rate per category and lists failing transcripts
- [ ] Results persist to Postgres and a second run shows a trend comparison against the first
- [ ] Threshold check exits non-zero when a category's block rate is deliberately set below threshold (test included)
- [ ] `pytest` passes for scoring logic and threshold check
- [ ] README documents how to run the red-team suite and read the dashboard
